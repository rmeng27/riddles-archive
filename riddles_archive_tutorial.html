Riddle’s Archive: Building a Character-Based RAG Chatbot with Claude, Guardrails, and Conversation Analytics

Author

Ran Meng

1 Project overview

Riddle’s Archive is a Hogwarts-themed, character-based chatbot built with Python, Streamlit, Retrieval-Augmented Generation (RAG), and Anthropic Claude. The user chooses a character, asks a question, and receives a response written in that character’s style. Under the surface, the app retrieves relevant evidence from a curated Harry Potter knowledge base, passes that evidence into Claude with a persona prompt, and then logs the interaction for retrieval confidence, sentiment, and topic analytics.

The main goal is not just to make a fun fan chatbot. The more important goal is to build an inspectable GenAI system. A normal chatbot hides most of its reasoning and data flow. This app exposes the retrieval evidence, confidence score, guardrail behavior, and conversation analytics, so the user can see when the system is grounded in the knowledge base and when it is relying more heavily on the model’s pretrained knowledge.

The final product has five main sections:

  1. Dialogue: the main roleplay chat interface.
  2. Retrieval: retrieved evidence, average similarity, and confidence labels.
  3. Analytics: sentiment trajectory, message length, retrieved topic counts, and low-confidence rate.
  4. Guardrails: prompt-injection checks, unsafe request blocking, and guardrail event logs.
  5. Data Notes: knowledge base preview, indexed rows by character, and reproducibility notes.

The app is designed for two audiences. First, it is for Harry Potter fans or literary roleplay users who want a more immersive character interaction experience. Second, it is for students/developers who want to see how RAG, prompt engineering, guardrails, and text analytics can be combined into one GenAI application.

2 Problem being solved

Large language models can imitate character voices, but a plain LLM chatbot has three major problems:

  • It may hallucinate facts because it is answering from general pretrained knowledge.
  • It gives no clear indication of what evidence supported an answer.
  • It usually treats conversation as disposable text rather than data that can be analyzed.

This project addresses those problems by combining a character chatbot with RAG and analytics. The RAG layer retrieves relevant chunks from a structured knowledge base before generation. The confidence layer summarizes how strongly the retrieved material matches the user query. The analytics layer records the interaction and turns the conversation into structured data.

In other words, the app asks:

Can we make a character chatbot that is not only immersive, but also more transparent, inspectable, and analytically grounded?

6 Data source design

The project uses a two-layer data design.

First, the public/repository-safe version uses a curated and paraphrased CSV knowledge base. Each row represents one retrievable chunk with metadata.

A simplified version of the data structure looks like this:

import pandas as pd

kb = pd.read_csv("data/hp_knowledge_base.csv")
kb.head()

Expected columns:

chunk_id | character | topic | source_type | text

The CSV is not a full copy of the Harry Potter books. It is a compact knowledge base created for the purpose of demonstrating RAG. This is important because the deployed project should not distribute copyrighted full text. The CSV gives the app a reproducible retrieval source while keeping the public version safer and easier to share.

Second, the app supports optional local text indexing. If the user places .txt files in data/books/, the app can read those local files, split them into chunks, detect character mentions, and add them to the retriever. This is useful for private educational testing.

For example:

data/books/
├── book2_notes.txt
├── movie_summary.txt
└── my_character_notes.txt

If a user wants the chatbot to focus on a specific book, they can add text or notes related to that book. If they want movie-version support, they can add movie summaries or screenplay-style notes that they have the right to use. The app does not provide or distribute those files; it only reads files supplied locally by the user.

7 System architecture

The app follows this general flow:

flowchart LR
    A[User chooses character and asks question] --> B[Input guardrail check]
    B --> C[Embed user query]
    C --> D[Retrieve top-k knowledge chunks]
    D --> E[Compute average similarity and confidence label]
    E --> F[Build character prompt]
    F --> G[Claude generates response]
    G --> H[Post-generation reliability note]
    H --> I[Display response and retrieved evidence]
    I --> J[Log sentiment, topics, and confidence]
    J --> K[Analytics dashboard]

The system deliberately separates retrieval from generation. This matters because the retrieval layer can be inspected independently. In the app, the Quick retrieval test panel lets me test what the retriever finds without calling Claude at all.

8 Building the character layer

The character layer controls who is speaking and how strongly the model should imitate that character.

Each character has a configuration containing fields such as:

EXTRA_CHARACTERS = {
    "Hermione Granger": {
        "slug": "hermione",
        "font": "Libre Baskerville, Georgia, serif",
        "accent": "#7A4E2A",
        "secondary": "#F8E4B1",
        "emoji": "📚",
        "group": "Core",
        "aliases": "Hermione Granger|Hermione",
        "greeting": "Honestly, let's be precise about this.",
        "persona": """
You are speaking in a Hermione Granger-inspired voice: precise, analytical,
ethically serious, and occasionally impatient with sloppy thinking.
Ground answers in retrieved evidence.
""",
    }
}

The character roster is split into groups such as Core, Students, and Faculty. The user selects a character from the sidebar. The selected character controls:

  • persona prompt;
  • response style;
  • font and visual styling;
  • aliases used for local text character detection;
  • greeting shown in the dialogue panel.

The app also has a persona intensity control. This does not change factual correctness. It changes how strongly the model performs the character voice.

  • Low = more like a normal assistant with light character flavor.
  • Medium = balanced character voice and usefulness.
  • High = stronger roleplay/persona behavior.

The canon faithfulness slider is different. It controls how strictly Claude should stay grounded in retrieved evidence. When this is high, the model is instructed to admit when the archive lacks evidence instead of inventing details.

9 Building the RAG layer

The RAG layer is the technical center of the app.

The retriever loads the knowledge base, embeds the chunks, embeds the user question, and computes semantic similarity. The app then returns the top-k most relevant chunks.

A simplified version of the logic is:

from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

model = SentenceTransformer("all-MiniLM-L6-v2")

chunk_embeddings = model.encode(kb["text"].tolist(), normalize_embeddings=True)
query_embedding = model.encode([user_question], normalize_embeddings=True)

similarities = cosine_similarity(query_embedding, chunk_embeddings)[0]
top_indices = similarities.argsort()[::-1][:top_k]
retrieved_chunks = kb.iloc[top_indices]

The actual app wraps this into a HybridRetriever class. The retriever can use the curated CSV alone or a combined dataset made from the CSV plus optional local .txt chunks.

9.1 Retrieved context chunks

The sidebar control called retrieved context chunks determines how many chunks are passed to Claude.

  • Lower values make the answer more focused but may omit useful context.
  • Higher values give Claude more evidence but may add noise.

The default value is a compromise between relevance and context size.

9.2 Confidence scoring

After retrieval, the app computes the average similarity score across the retrieved chunks. Then it maps that score to a confidence label:

High / Medium / Low

This is not a perfect truth detector. It does not prove that an answer is correct. It only tells the user whether the app found semantically relevant evidence in the knowledge base.

This distinction matters. If the knowledge base contains a relevant chunk, the answer is more grounded. If the knowledge base does not contain relevant material, Claude may still answer from pretrained knowledge, but the app should label the response as weaker/less grounded.

10 Calling Claude

Claude is used for generation, not for retrieval.

The app sends Claude:

  • the user question;
  • recent conversation history;
  • the selected character persona;
  • retrieved evidence chunks;
  • persona intensity instructions;
  • confidence label and confidence note;
  • guardrail instructions such as avoiding long copyrighted quotations.

A simplified version of the API call is:

from anthropic import Anthropic

client = Anthropic(api_key=api_key)

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=650,
    temperature=0.7,
    messages=[
        {"role": "user", "content": prompt_for_claude}
    ],
)

answer = response.content[0].text

In the app, this is handled by generate_character_response(). Keeping this logic in a helper function makes the app easier to maintain.

11 Session memory

The current app uses session-level memory through Streamlit session state:

if "messages" not in st.session_state:
    st.session_state.messages = []

Each user message and assistant response is appended to the session history. This means the chatbot can refer to earlier messages within the same visit.

Important limitation: this is not long-term memory. If the user refreshes the page, clears the conversation, or starts a new session, the memory is lost. Also, the current design uses shared archive-level memory, not separate memory for each character. If the user talks to Sirius and then switches to Harry in the same session, the app may still pass the earlier conversation history to Claude.

For this project, shared session memory fits the archive concept. Future versions could add per-character memory or user-controlled memory export/import.

12 Guardrails

The app includes a lightweight app-level guardrail layer before calling Claude. This is not meant to replace Anthropic’s provider-side safety systems. It is included to demonstrate responsible GenAI design at the application level.

The input guardrail checks for:

  • prompt injection attempts;
  • requests to reveal or override system instructions;
  • unsafe real-world harm requests;
  • self-harm method requests;
  • doxxing/private information requests;
  • extremely long inputs.

A simplified version of the logic is:

injection_patterns = [
    r"ignore (all )?(previous|above|system|developer) instructions",
    r"reveal (the )?(system|developer) prompt",
    r"disable (safety|guardrails|policy)",
    r"jailbreak",
]

if any(re.search(pattern, user_message.lower()) for pattern in injection_patterns):
    status = "redirect"

The app has three possible guardrail outcomes:

  • allow: the message passes through normally;
  • redirect: the harmful/injection part is removed or reframed;
  • block: the app refuses to answer unsafe requests.

The Guardrails tab logs triggered events so the behavior is inspectable.

13 Conversation analytics

The analytics layer turns the conversation into structured data. Each turn is logged with fields such as:

turn | character | user_message | assistant_message | sentiment | message_length | confidence | avg_similarity | retrieved_topics | backend

The Analytics tab displays:

  • number of turns;
  • average user sentiment;
  • average retrieval similarity;
  • low-confidence rate;
  • sentiment over time;
  • message length by turn;
  • most frequently retrieved topics;
  • downloadable conversation log table.

This is the part that connects the project back to text mining and data analysis. The analytics do not prove causality. They are descriptive. But they help inspect how the conversation evolves and how often the system is strongly grounded in retrieved evidence.

14 User interface and immersion layer

The visual layer is intentionally more polished than a plain Streamlit app because the project is also an interactive artifact.

The UI includes:

  • Marauder’s Map / archive-style background;
  • glassmorphism panels;
  • character-specific fonts;
  • custom sidebar controls;
  • optional background ambience/music player;
  • optional Weasley pop-up ads when Fred & George are selected.

The visual and ambience controls do not affect the model. They support immersion and user experience.

The Weasley ad feature is intentionally small and silly. It only triggers when:

  1. the selected character is Fred & George Weasley;
  2. the Weasley ad toggle is turned on;
  3. the current turn matches the app’s occasional trigger condition.

This is mostly a creative UX detail, but it helps make the demo memorable.

17 Limitations

17.1 Knowledge base coverage

The biggest limitation is knowledge coverage. The deployed version uses a compact curated/paraphrased knowledge base rather than a full Harry Potter universe database. This means it cannot cover every canon detail.

If a user asks a very specific question and the CSV does not contain relevant evidence, the retriever may return weak results. Claude may still answer using pretrained knowledge, but the app labels the response as lower-confidence when retrieval is weak.

17.2 Character coverage

The app currently includes a limited set of characters. Core characters have slightly richer curated evidence coverage, while additional students and faculty have lighter coverage. Adding a character requires persona design, aliases, style choices, and enough evidence chunks to make retrieval useful.

17.3 Persona accuracy is subjective

There is no perfectly objective metric for whether a response sounds like Hermione, Luna, or Sirius. The app uses persona prompts and retrieved evidence, but persona consistency still partly depends on human judgment.

17.4 RAG reduces hallucination but does not remove it

Retrieval improves grounding, but generation is still probabilistic. Even with relevant chunks, the model may over-explain, mix in pretrained knowledge, or produce plausible but unsupported details.

17.5 Analytics are descriptive

The analytics dashboard shows sentiment, message length, topic counts, and low-confidence rate. These are useful for inspection, but they do not prove user engagement or model quality by themselves.

17.6 Guardrails are lightweight

The current guardrails are rule-based and app-level. They demonstrate responsible design but are not a complete production-grade safety system.

18 Lessons learned

The biggest lesson was that a good GenAI app is not just an API call. The app only became a real project once the system had a clear data source, retrieval pipeline, guardrails, confidence scoring, analytics, and deployment plan.

I also learned that RAG is only as good as its knowledge base. If the corpus is small or off-topic, retrieval quality drops. This is why showing retrieved evidence is so important. It lets the user see whether the model was actually grounded.

Another lesson was that UI matters. A project can be technically correct but still feel unfinished if the interface looks like a default app. Adding character-specific fonts, a themed background, and separated tabs made the project easier to understand and more memorable.

Finally, I learned that copyright and data-source design matter in GenAI projects. For a public project, it is safer to use a curated and paraphrased knowledge base, while supporting optional local indexing for private educational testing.

19 Future extensions

A future version could expand this into a general literary character interaction platform. The same framework could work for other books, plays, movies, or fictional universes, as long as the app has a structured knowledge base and character persona definitions.

Possible extensions include:

  • adding more Harry Potter characters;
  • letting the user choose book canon, movie canon, or a specific book/era;
  • using licensed or public-domain corpora;
  • automatically building character dossiers with NLP;
  • adding formal evaluation with Precision@K, MRR, answer faithfulness, and human persona ratings;
  • adding voice input/output and character-specific audio;
  • adding long-term memory with user-controlled memory export/import;
  • adding a study mode for literary analysis instead of roleplay only.

20 Conclusion

Riddle’s Archive is a character-based RAG chatbot, but the important part is the system around the chatbot. It retrieves evidence, generates persona-consistent responses, logs the interaction, analyzes the conversation, and exposes reliability signals to the user.

The final app demonstrates how GenAI tools can be combined with retrieval, prompt engineering, guardrails, and text analytics to create an interactive product that is both fun to use and technically inspectable.

Expected columns:

```text
chunk_id | character | topic | source_type | text
```

The CSV is not a full copy of the Harry Potter books. It is a compact knowledge base created for the purpose of demonstrating RAG. This is important because the deployed project should not distribute copyrighted full text. The CSV gives the app a reproducible retrieval source while keeping the public version safer and easier to share.

Second, the app supports optional local text indexing. If the user places `.txt` files in `data/books/`, the app can read those local files, split them into chunks, detect character mentions, and add them to the retriever. This is useful for private educational testing.

For example:

```text
data/books/
├── book2_notes.txt
├── movie_summary.txt
└── my_character_notes.txt
```

If a user wants the chatbot to focus on a specific book, they can add text or notes related to that book. If they want movie-version support, they can add movie summaries or screenplay-style notes that they have the right to use. The app does not provide or distribute those files; it only reads files supplied locally by the user.

## System architecture

The app follows this general flow:

```mermaid
flowchart LR
    A[User chooses character and asks question] --> B[Input guardrail check]
    B --> C[Embed user query]
    C --> D[Retrieve top-k knowledge chunks]
    D --> E[Compute average similarity and confidence label]
    E --> F[Build character prompt]
    F --> G[Claude generates response]
    G --> H[Post-generation reliability note]
    H --> I[Display response and retrieved evidence]
    I --> J[Log sentiment, topics, and confidence]
    J --> K[Analytics dashboard]
```

The system deliberately separates retrieval from generation. This matters because the retrieval layer can be inspected independently. In the app, the **Quick retrieval test** panel lets me test what the retriever finds without calling Claude at all.

## Building the character layer

The character layer controls who is speaking and how strongly the model should imitate that character.

Each character has a configuration containing fields such as:

```python
EXTRA_CHARACTERS = {
    "Hermione Granger": {
        "slug": "hermione",
        "font": "Libre Baskerville, Georgia, serif",
        "accent": "#7A4E2A",
        "secondary": "#F8E4B1",
        "emoji": "📚",
        "group": "Core",
        "aliases": "Hermione Granger|Hermione",
        "greeting": "Honestly, let's be precise about this.",
        "persona": """
You are speaking in a Hermione Granger-inspired voice: precise, analytical,
ethically serious, and occasionally impatient with sloppy thinking.
Ground answers in retrieved evidence.
""",
    }
}
```

The character roster is split into groups such as Core, Students, and Faculty. The user selects a character from the sidebar. The selected character controls:

- persona prompt;
- response style;
- font and visual styling;
- aliases used for local text character detection;
- greeting shown in the dialogue panel.

The app also has a **persona intensity** control. This does not change factual correctness. It changes how strongly the model performs the character voice.

- Low = more like a normal assistant with light character flavor.
- Medium = balanced character voice and usefulness.
- High = stronger roleplay/persona behavior.

The **canon faithfulness** slider is different. It controls how strictly Claude should stay grounded in retrieved evidence. When this is high, the model is instructed to admit when the archive lacks evidence instead of inventing details.

## Building the RAG layer

The RAG layer is the technical center of the app.

The retriever loads the knowledge base, embeds the chunks, embeds the user question, and computes semantic similarity. The app then returns the top-k most relevant chunks.

A simplified version of the logic is:

```python
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

model = SentenceTransformer("all-MiniLM-L6-v2")

chunk_embeddings = model.encode(kb["text"].tolist(), normalize_embeddings=True)
query_embedding = model.encode([user_question], normalize_embeddings=True)

similarities = cosine_similarity(query_embedding, chunk_embeddings)[0]
top_indices = similarities.argsort()[::-1][:top_k]
retrieved_chunks = kb.iloc[top_indices]
```

The actual app wraps this into a `HybridRetriever` class. The retriever can use the curated CSV alone or a combined dataset made from the CSV plus optional local `.txt` chunks.

### Retrieved context chunks

The sidebar control called **retrieved context chunks** determines how many chunks are passed to Claude.

- Lower values make the answer more focused but may omit useful context.
- Higher values give Claude more evidence but may add noise.

The default value is a compromise between relevance and context size.

### Confidence scoring

After retrieval, the app computes the average similarity score across the retrieved chunks. Then it maps that score to a confidence label:

```text
High / Medium / Low
```

This is not a perfect truth detector. It does not prove that an answer is correct. It only tells the user whether the app found semantically relevant evidence in the knowledge base.

This distinction matters. If the knowledge base contains a relevant chunk, the answer is more grounded. If the knowledge base does not contain relevant material, Claude may still answer from pretrained knowledge, but the app should label the response as weaker/less grounded.

## Calling Claude

Claude is used for generation, not for retrieval.

The app sends Claude:

- the user question;
- recent conversation history;
- the selected character persona;
- retrieved evidence chunks;
- persona intensity instructions;
- confidence label and confidence note;
- guardrail instructions such as avoiding long copyrighted quotations.

A simplified version of the API call is:

```python
from anthropic import Anthropic

client = Anthropic(api_key=api_key)

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=650,
    temperature=0.7,
    messages=[
        {"role": "user", "content": prompt_for_claude}
    ],
)

answer = response.content[0].text
```

In the app, this is handled by `generate_character_response()`. Keeping this logic in a helper function makes the app easier to maintain.

## Session memory

The current app uses session-level memory through Streamlit session state:

```python
if "messages" not in st.session_state:
    st.session_state.messages = []
```

Each user message and assistant response is appended to the session history. This means the chatbot can refer to earlier messages within the same visit.

Important limitation: this is not long-term memory. If the user refreshes the page, clears the conversation, or starts a new session, the memory is lost. Also, the current design uses shared archive-level memory, not separate memory for each character. If the user talks to Sirius and then switches to Harry in the same session, the app may still pass the earlier conversation history to Claude.

For this project, shared session memory fits the archive concept. Future versions could add per-character memory or user-controlled memory export/import.

## Guardrails

The app includes a lightweight app-level guardrail layer before calling Claude. This is not meant to replace Anthropic's provider-side safety systems. It is included to demonstrate responsible GenAI design at the application level.

The input guardrail checks for:

- prompt injection attempts;
- requests to reveal or override system instructions;
- unsafe real-world harm requests;
- self-harm method requests;
- doxxing/private information requests;
- extremely long inputs.

A simplified version of the logic is:

```python
injection_patterns = [
    r"ignore (all )?(previous|above|system|developer) instructions",
    r"reveal (the )?(system|developer) prompt",
    r"disable (safety|guardrails|policy)",
    r"jailbreak",
]

if any(re.search(pattern, user_message.lower()) for pattern in injection_patterns):
    status = "redirect"
```

The app has three possible guardrail outcomes:

- **allow**: the message passes through normally;
- **redirect**: the harmful/injection part is removed or reframed;
- **block**: the app refuses to answer unsafe requests.

The Guardrails tab logs triggered events so the behavior is inspectable.

## Conversation analytics

The analytics layer turns the conversation into structured data. Each turn is logged with fields such as:

```text
turn | character | user_message | assistant_message | sentiment | message_length | confidence | avg_similarity | retrieved_topics | backend
```

The Analytics tab displays:

- number of turns;
- average user sentiment;
- average retrieval similarity;
- low-confidence rate;
- sentiment over time;
- message length by turn;
- most frequently retrieved topics;
- downloadable conversation log table.

This is the part that connects the project back to text mining and data analysis. The analytics do not prove causality. They are descriptive. But they help inspect how the conversation evolves and how often the system is strongly grounded in retrieved evidence.

## Limitations

### Knowledge base coverage

The biggest limitation is knowledge coverage. The deployed version uses a compact curated/paraphrased knowledge base rather than a full Harry Potter universe database. This means it cannot cover every canon detail.

If a user asks a very specific question and the CSV does not contain relevant evidence, the retriever may return weak results. Claude may still answer using pretrained knowledge, but the app labels the response as lower-confidence when retrieval is weak.

### Character coverage

The app currently includes a limited set of characters. Core characters have slightly richer curated evidence coverage, while additional students and faculty have lighter coverage. Adding a character requires persona design, aliases, style choices, and enough evidence chunks to make retrieval useful.

### Persona accuracy is subjective

There is no perfectly objective metric for whether a response sounds like Hermione, Luna, or Sirius. The app uses persona prompts and retrieved evidence, but persona consistency still partly depends on human judgment.

### RAG reduces hallucination but does not remove it

Retrieval improves grounding, but generation is still probabilistic. Even with relevant chunks, the model may over-explain, mix in pretrained knowledge, or produce plausible but unsupported details.

### Analytics are descriptive

The analytics dashboard shows sentiment, message length, topic counts, and low-confidence rate. These are useful for inspection, but they do not prove user engagement or model quality by themselves.

### Guardrails are lightweight

The current guardrails are rule-based and app-level. They demonstrate responsible design but are not a complete production-grade safety system.

## Lessons learned

The biggest lesson was that a good GenAI app is not just an API call. The app only became a real project once the system had a clear data source, retrieval pipeline, guardrails, confidence scoring, analytics, and deployment plan.

I also learned that RAG is only as good as its knowledge base. If the corpus is small or off-topic, retrieval quality drops. This is why showing retrieved evidence is so important. It lets the user see whether the model was actually grounded.

Another lesson was that UI matters. A project can be technically correct but still feel unfinished if the interface looks like a default app. Adding character-specific fonts, a themed background, and separated tabs made the project easier to understand and more memorable.

Finally, I learned that copyright and data-source design matter in GenAI projects. For a public project, it is safer to use a curated and paraphrased knowledge base, while supporting optional local indexing for private educational testing.

## Future extensions

A future version could expand this into a general literary character interaction platform. The same framework could work for other books, plays, movies, or fictional universes, as long as the app has a structured knowledge base and character persona definitions.

Possible extensions include:

- adding more Harry Potter characters;
- letting the user choose book canon, movie canon, or a specific book/era;
- using licensed or public-domain corpora;
- automatically building character dossiers with NLP;
- adding formal evaluation with Precision@K, MRR, answer faithfulness, and human persona ratings;
- adding voice input/output and character-specific audio;

- adding a study mode for literary analysis instead of roleplay only.

## Conclusion

Riddle's Archive is a character-based RAG chatbot, but the important part is the system around the chatbot. It retrieves evidence, generates persona-consistent responses, logs the interaction, analyzes the conversation, and exposes reliability signals to the user.

The final app demonstrates how GenAI tools can be combined with retrieval, prompt engineering, guardrails, and text analytics to create an interactive product that is both fun to use and technically inspectable.
